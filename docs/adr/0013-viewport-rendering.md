# 0013 Viewport rendering: exact parallel tiles off the UI thread; vello leaves the GUI

- Context: the canvas rasterised the whole page synchronously on the UI thread whenever the revision or zoom changed (about 23 ms a keystroke at 144 dpi, plan Locked Decision 3), into a texture capped at 4,096 px (blurry beyond about 500%). Plan T5 asks for viewport-sized renders at device resolution on a worker thread, parallel tiles byte-identical to the single-threaded render (Locked Decision 4, Risk 2), damage repaint, image mips, and a decision on vello.
- Decision:
  - **Tiles share the region's transform and clip.** Pixel-aligned tiles with an integer offset in the transform are *not* exact with tiny-skia: path coordinates round differently in f32, the edge clipper chops edges at tile seams and recomputes their slopes, and image sampling maps different pixel centres. Measured with 64 px translated tiles against the untiled render of the golden pages: 616, 600, 676, 15 and 592 differing channels (shapes, text, images, master and bleed, stress page), up to 85 levels. So every tile is drawn into a scratch pixmap the size of the whole *region* with the region's own transform. Each pixel then depends only on the primitives over it and its starting value, so a tile is exact if it starts from the background, every primitive whose conservative device box touches it is drawn in paint order, and only its pixels are read back. Axis-aligned rectangles and image clips are cut to the tile plus 2 px (vertical edges keep their bit-identical x, rows inside stay fully covered), glyphs outside the tile are skipped one by one, opacity layers are drawn into a second region-sized scratch and composited over the tile only with the pattern paint `draw_pixmap` uses, and SVG sub-pixmaps are composited over the tile only. `crates/pubrs-render/tests/tiles.rs` renders every golden page (built in the test like `render_golden.rs`) plus a stress page tiled at 1, 2, 7 and 16 threads with automatic and odd tile sizes (37×23, 101×13, 7×61, full-width 1-row bands) and compares byte for byte; offset regions with damage-style rectangles and mips are compared the same way. Goldens stay rendered untiled and unchanged.
  - **A region** is the visible pixels plus 25% of the viewport per side, clipped to the page raster and to the GPU's `max_texture_side` (the margin shrinks first), at 72 × zoom × pixels-per-point dpi. Only if the visible pixels alone exceed the largest texture is the resolution lowered and the texture drawn scaled. The view key holds the page raster size, so a page size or bleed change at the same zoom is a new render. `Region::page` is exactly the old page render, so `RasterRenderer::render` is unchanged.
  - **Memory.** Region-sized scratches cost memory per thread. `TileOptions::auto` uses at most 8 threads (16 measured no faster: allocation dominates), `SCRATCH_BUDGET` (160 MB, counting the opacity layer each thread needs when the scene has translucent nodes) caps how many scratches exist at once (a huge region gets fewer threads), and two scratches stay pooled between calls, without their layers, so damage repaints allocate nothing.
  - **Damage** (`damage.rs`): old and new bounds of touched frames, taken from what the editor's scene draws for them (fills, strokes grown by twice their width, empty-picture placeholders whose 1 pt diagonals poke past the frame, image clips, text ink, through the rotation), frames added, removed or restacked, every changed line of text frames whose story was recomposed (font bounding box per glyph), image frames of touched assets; merged and clipped per page. `Touched` comes from the session's change log; for revisions it lacks (undo, redo) the page's frames are compared by `Arc` pointer instead.
  - **Worker** (`pubrs-app/src/render_worker.rs`): newest request wins; the worker diffs against the snapshot it last drew, so dropping a stale request is safe. Each job runs under `catch_unwind` (tile threads re-raise their own panic message); a failure is reported to the UI, the worker forgets its last drawing, and the UI asks again up to three times. If the thread is gone, `poll` reports it and the app starts a new worker (up to three times), showing a status message. The UI uploads only damaged rectangles (`set_partial`) and shows the old texture scaled until a new one lands. Thumbnails move to the worker too.
  - **Mips**: `RasterImage::mips` (2×2 box reductions of premultiplied pixels, built on first use); sampled only when `Region::mips` is set, which only the GUI does (the viewport and the page panel's thumbnails).
  - **vello leaves the GUI.** Measured on this machine's only adapter (llvmpipe, 16 cores; a hardware GPU was not available): vello whole page at 144 dpi 15.9 ms against 6.6 ms for tiles; at 400%, vello must draw the whole 4896×6336 page (190 ms) against 24.9 ms for the 4320×2700 viewport region; device creation 96 ms. vello cannot draw only a damaged strip seamlessly (its anti-aliasing differs from tiny-skia's and between adapters; the M3 test allows a mean channel difference, not identity), while a tiled 1200×60 damage strip costs 1.3 ms. On real GPUs vello is faster than llvmpipe, but the readback and the full-page redraw per edit remain. So the viewport (and thumbnails) use tiled tiny-skia everywhere, and the screen shows the same pixels PNG export writes. vello stays behind the `gpu` feature for `Session::page_rgba` only (one-shot whole pages for API clients), "only for export" in the plan's terms.
- Consequence:
  - `pubrs perf` (16-core development machine, release, median of 5): viewport at 100% (2880×1800 on HiDPI) 6.4 ms at 200 pages (enforced ≤ 16 ms; 6.4 to 9.4 ms over several runs on a loaded machine) and 6.3 ms at 50 (CI bound 40 ms); keystroke = command + layout + damage repaint 8.4 ms at 200 pages (enforced ≤ 30 ms; was 31.4 ms with the full re-render) and 7.8 ms at 50 (CI bound 60 ms). A keystroke repaints about 1.2% of the page.
  - The GUI self-test zooms to 800% and checks a pixel-aligned edge is sharp on screen, and types into a 50-page publication checking that no page is rasterised on the UI thread and that UI-thread work besides commands and layout stays under 50 ms a frame (measured 2.3 to 2.7 ms in the debug build).
  - The app still enables `pubrs-api/gpu`, so vello is compiled into it though no GUI path uses it (TODO.md).
- Addendum (M15): the self-test's typing check now tolerates one scheduler outlier. On the shared macos-15-intel runner one frame took 115.7 ms of UI-thread time besides commands and layout (CI run 38119566661); the re-run measured 5.4 ms, and this machine 2.5 to 2.7 ms. The real assertions are now that no page is rasterised on the UI thread and that the **second-worst** frame stays within 50 ms (unchanged limit); the single worst frame is only bounded at 250 ms, so a stall that repeats still fails. No `pubrs perf` budget changed.
