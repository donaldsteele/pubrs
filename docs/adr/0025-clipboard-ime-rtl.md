# 0025 Clipboard, input methods and right-to-left carets

- Context: T19 (M27). Publisher pastes pictures and text from other programs, copies frames between open publications, composes CJK text through an input method, and edits Hebrew and Arabic with a caret that follows the screen. Until now copy/paste was one publication only, text editing took direct key input only, and carets assumed left-to-right lines. Locked Decisions 3 (nothing new on the keystroke path), 4 (goldens unchanged) and ADR 0005 (allocate ids before building commands) bind.
- Decision:
  - **Clipboard trait.** `Clipboard` gains `get_image`/`set_image` (straight RGBA plus size, `ClipImage`) and `get_html`/`set_html(html, alt_text)` beside the text pair. `DesktopClipboard` uses arboard 3.6.1 (`image-data` is already on; no new crate). `NoClipboard` (self-test, null platform) keeps text, HTML and an image in memory and, like the real clipboard, each `set_*` replaces the others. The per-OS files are unchanged: arboard replaces the whole clipboard on every set and only HTML plus a text alternative can coexist, so a native multi-format path (pubrs flavour plus PNG plus text in one clipboard offer) is a TODO.
  - **Copying frames.** One HTML string: `<div data-pubrs="1"><!--pubrs:BASE64--><img src="data:image/png;base64,...">`. The comment holds a `ClipPayload` as JSON (frames in preorder with group members, stories, assets with bytes, the styles the text uses with their base styles, and the full-strength colour of each swatch used). The `<img>` is the selection's page area at 96 dpi, cropped from a page render, for programs that paste images out of HTML. The text alternative is the frames' text (or "pubrs frames"). The payload is also kept in the app (`InProcessClip`, with the alternative text as a marker): it is used when the OS clipboard still holds our marker text or nothing, so a selection too big for the clipboard (HTML over 48 MB is not put there) still pastes inside this run.
  - **Paste order.** (1) HTML carrying a pubrs payload, or our own in-process payload: paste frames, cross-document included; (2) not editing and an image: a picture frame; (3) editing and HTML: reduced rich runs; (4) text: inserted at the caret, or, with no text being edited, a new text frame. While text is being edited a pubrs payload pastes as its text (the same text as the plain-text alternative, table cells tab-separated by row), never as frames.
  - **Cross-document paste.** `Session::clip_copy` and `Session::clip_paste` (also behind the MCP tool `frame_copy_to_doc {from_doc_id, frame_ids, to_doc_id, page_index, offset?}`) build one `Batch`: every frame, story, group and asset id is allocated first; members of a copied group are copied with it and the group is made again with `Group` (innermost first); a text frame whose chain is only partly copied keeps the copied part as a chain (the first frame holds the text, the others are added empty and joined with `LinkFrames`); locks and template placeholder marks are dropped (as `frame_duplicate` does); an asset the target already holds with identical bytes, size and format is reused, else it is added under a new id; paragraph and character styles are matched by kind and name first (a style with the same id but another name is never adopted), a missing one is added under a new id (based on its base style if that was matched), a name taken by a style of another kind drops to the default; swatches are kept only if the target has one with the same id and name, else the target's swatch of that name is used, else the swatch becomes its colour (tint applied), in frames, text, styles and table cell fills and borders; a copied group keeps its name, style and wrap (not its rotation, which would rotate the members again, TODO). A table is copied with a new story per cell (ids allocated up front, each story listing only the new table frame, text copied, styles and swatches mapped like any story) and added with `AddTable`, as `frame_duplicate` does; its cell text is part of the plain-text alternative. The code is generic over `FrameContent`: it clones the frame, then fixes up only image assets and text stories, so a later content kind needs only its own references handled. One undo step.
  - **HTML to runs.** A tolerant tokenizer, not a parser: `b/strong` (and headings, `th`), `i/em/cite`, `u/ins`, `font color`, and `style` declarations `font-weight`, `font-style`, `text-decoration`, `font-size` (pt, px), `color` (hex, `rgb()`, nine names). Block tags make paragraphs, `br` a line, `script/style/head/title` are dropped, entities decoded, whitespace collapsed outside `pre`. Everything else is its text. The runs go in as one `InsertText`/`ReplaceText` plus `ApplyCharProps` per formatted run, in one `Batch`. RTF is not read: arboard has no RTF format, and no OS gives it to us without a native path (TODO).
  - **Pictures.** `pubrs_io::rgba_to_png` encodes the pixels as PNG, scaling down with a triangle filter when a side is over `PASTE_MAX_SIDE` (8,000), then the normal `frame_add_image` path applies (`MAX_IMAGE_PIXELS` 20,000, 64 MB). The frame is the image at 96 dpi, shrunk to 80% of the page if larger, centred; the status line says "scaled down" with both sizes. Ctrl+V (Windows, Linux) does nothing for an image-only clipboard: egui-winit 0.36.2 handles the paste shortcut by reading clipboard text, pushes `Event::Paste` only if there is some, and returns without sending a key event, so neither the shortcut table nor `raw_input_hook` (which sees modifiers but no key) can tell that V was pressed; the menu item works, and on macOS the native menu's Cmd+V key equivalent runs the action (TODO).
  - **Input methods.** `egui::Event::Ime`: `Preedit` stores the text and its active range in `TextEdit.preedit`, drawn at the caret on a plain backing with an underline (thicker under the active part) in the UI font; nothing reaches the document, so no command, no layout, no undo step. `Commit` clears the preedit and goes through `edit_insert`, the coalesced typing path (`type-{story}`), so it merges with typing before it. `DeleteSurrounding` deletes the characters around the selection as one batch and moves the caret. Every frame while editing, `ctx.output.ime` gets the text frame's screen box and a one-pixel caret rect placed after the preedit; egui-winit turns that into the window's IME area, which puts the candidate window at the caret.
  - **Right-to-left.** Carets were already taken from parley cursors, so a right-to-left line's carets fall as the offset rises; `LineBox::caret_x` looks up by offset and `offset_at_x` takes the nearest x, neither assumes monotonic x. New on `LineBox`: `spans` (only for lines that can reorder: parley says the paragraph runs right to left, or the line has a character from a right-to-left block; empty otherwise, so lines in reading order cost nothing and compare equal to before) holds each character's box as offsets from its caret (left of it for a right-to-left character); `slots()` adds, for each offset whose previous character lies the other way, that character's trailing edge as a second caret place (at a Hebrew word inside English text the leading edge of the first letter and the place after the last are far apart; both offsets then have two places); `slot_at_x`, `slot_x`, `visual_step`, `visual_edge`, `selection_spans`, `is_rtl`. The GUI: Left/Right on bidi lines go to the nearest slot on that side (equal x: the offset nearest the current one), at the line's visual end they continue through the text in the direction the edge leads to; Ctrl/Alt+arrows swap direction in right-to-left lines; Home/End go to the line's start/end edge (the right end for a right-to-left line); click and drag use the nearest slot; selections draw one quad per visual piece; the caret is drawn at the slot it was placed at (`TextEdit.visual_x`, cleared by anything that moves the caret otherwise). Lines in reading order take exactly the old code.
  - **Untrusted input.** The clipboard may hold anything, so a paste is bounded and checked. Reading: HTML without a pubrs marker over 4 MiB is pasted as plain text; the base64 section of a payload is refused over 96 MiB, the JSON over 64 MiB; after parsing at most 5,000 frames, 20,000 stories, 256 images, 2,000 styles and 2,000 swatches, 200,000 paragraphs, 400,000 runs and 32 MiB of text (the model has no such limits of its own); plain text is cut at 1,000,000 characters. The HTML reducer follows 64 nested tags, keeps at most 200,000 characters and 10,000 runs, decodes entities within a 12-byte window, and says when it cut. Pasting: every image is sniffed with `image_info` from its bytes (format and size come from there, never from the JSON; at most 64 MB and 20,000 px a side) and a bad one refuses the whole paste; a picture whose image is not in the payload, a table that fails `TableFrame::check`, a text frame with columns outside 1-12 or bad insets, and repeated ids refuse it too; stories with no paragraphs get one; a group left with fewer than two members is not made (its member stays on the page, and only the frames really created are returned); the finished `Batch` is applied to a copy of the document and `check_integrity` must pass on the copy before the real document is touched.
- Consequence:
  - Two offsets can share a visual place (4 and 8 at the left edge of a Hebrew word in "abc שלום def"); arrow walks to the right take the first, to the left the second, so each is reachable but not both in each direction.
  - The preedit is drawn with the UI font, which has no CJK glyphs unless the system supplies them to egui; the committed text uses the document fonts.
  - Tab stops in right-to-left paragraphs still measure from the left edge (TODO).
  - The pubrs payload on the OS clipboard is base64 inside base64 (JSON, then HTML comment): about 1.8 times the asset bytes.
  - A pasted picture is a PNG even if the clipboard image came from a photo; it is not recompressed as JPEG.
